# 專案學習指南（Learning Guide）

這份文件的目的，是讓這個專案不只是「把 App 做出來」，而是讓開發者在過程中逐步理解軟體開發。

不要求一次全部學會，而是跟著專案進度學。

---

## Phase 0 — 需求探索

### 這個階段在做什麼？

先搞清楚「要做什麼」，而不是急著寫程式。

### 應該學會

- 什麼是產品需求。
- 使用者需求和功能清單有什麼不同。
- 什麼是使用情境（User Scenario）。
- 什麼是 MVP（Minimum Viable Product，最小可行產品）。
- 為什麼需要限制專案範圍。

### 完成標準

至少可以清楚回答：

1. 這個 App 給誰用？
2. 他遇到什麼問題？
3. App 最重要的價值是什麼？
4. 第一版一定要有哪幾個功能？
5. 哪些功能第一版不要做？

---

## Phase 1 — 使用流程與 UI 設計

### 這個階段在做什麼？

把需求轉換成實際操作流程與畫面。

### 應該學會

- User Flow（使用者流程）是什麼。
- Wireframe（線框圖）是什麼。
- UI 與 UX 的差異。
- 為什麼畫面不是「漂亮就好」。
- 如何從使用者任務推導出畫面。

### 完成標準

可以從 App 啟動開始，描述使用者如何完成最核心的任務。

---

## Phase 2 — Unity 專案基礎

### 這個階段在做什麼？

正式建立 Unity 專案，但先理解基本結構，不急著塞入大量功能。

### 應該學會

- Unity Project 是什麼。
- Scene（場景）是什麼。
- GameObject 是什麼。
- Component（元件）是什麼。
- Prefab（預製物件）是什麼。
- Script 為什麼使用 C#。
- Assets 目錄應該如何整理。

### 完成標準

能打開專案並大致知道重要資料放在哪裡。

---

## Phase 3 — 第一個核心功能

### 這個階段在做什麼？

只實作 MVP 最核心的一條流程。

### 應該學會

- 一個需求如何拆成程式任務。
- UI 和程式邏輯如何連接。
- 狀態與資料如何保存。
- Debug（除錯）基本觀念。
- 為什麼不要一次做所有功能。

### 完成標準

至少有一條真正可以操作的完整核心流程。

---

## Phase 4 — Git / GitHub 開發流程

### 這個階段在做什麼？

利用真實開發工作來理解版本控制，而不是只背 Git 指令。

### 應該學會

- Repository 是什麼。
- Commit 是什麼。
- Branch 是什麼。
- Pull Request 是什麼。
- Merge 是什麼。
- 為什麼修改程式前要知道自己在哪個 branch。
- 如何從 Git 歷史看出專案發生過什麼。

### AI 的責任

當要求你執行 Git 指令時，不能只給指令。

例如：

```bash
git status
```

同時要說明：

> 這個指令不會修改任何檔案，它只是查看目前 Git 工作區的狀態，例如有哪些檔案被修改、目前位於哪個分支。

讓你逐步知道自己正在允許什麼。

---

## Phase 5 — 測試與驗證

### 這個階段在做什麼？

學會「程式跑得起來」不等於「功能正確」。

### 應該學會

- Test Case（測試案例）。
- Acceptance Criteria（驗收條件）。
- Manual Test（人工測試）。
- Automated Test（自動化測試）。
- Regression（修改新功能後造成舊功能壞掉）。

### 完成標準

每個主要需求都有方法確認它真的正常。

---

## Phase 6 — AI 協作開發

### 這個階段在做什麼？

學習怎麼讓 AI 真的成為工程助手，而不是黑盒代工。

### 應該學會

- 怎麼提供 AI 足夠的 Context（上下文）。
- 為什麼規格要寫在 repository，而不能只在聊天裡。
- 如何讓 AI 先 Plan 再 Implement。
- 如何 Review AI 的修改。
- 如何讓不同 AI 接手同一專案。
- AI 哪些事情可以自動做，哪些事情應該人工決定。

# AI 指令授權的學習規則

未來如果 AI 要你批准 Terminal / Shell 指令，應該盡量標示風險。

## 🟢 讀取型

例如：

```text
git status
git log
ls
dir
```

通常只是查看資料，不修改檔案。

## 🟡 修改型

例如：

```text
git add
git commit
npm install
```

會修改 Git 狀態、專案檔案或安裝套件，需要知道原因。

## 🔴 高影響型

例如：

```text
git reset --hard
rm -rf
git push --force
```

可能刪除資料或覆蓋 Git 歷史，AI 必須特別解釋，不應要求開發者習慣性批准。

---

# 最終目標

理想狀態不是：

> 「AI 很厲害，所以 App 做好了。」

而是：

> 「AI 幫我加速開發，而我知道需求怎麼形成、Unity 怎麼組成、Git 在做什麼、如何測試，也知道怎麼判斷 AI 提出的方案是否合理。」
